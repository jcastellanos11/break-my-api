## Architecture and data flow

```text
main.tsx -> I18nProvider -> App (foundation preview)
                              |
                 localized copy only; no running engine yet

P1.3 controller will explicitly call:
config -> createSimulation -> advanceSimulation(state, deltaMs)
                                    |
                arrival -> limiter -> eligible GET cache
                              |              |
                             429        HIT -> scheduled 200
                                             |
                           MISS -> free origin slot -> scheduled 200
                                      |
                               bounded FIFO queue -> origin when free
                                      |
                              no waiting room -> 503
                                    |
                  counters + 1s buckets + bounded transient event log
                                    |
                       getSimulationSnapshot -> future React view
```

All requests are fictional `GET /api/products`, hence cache eligible. No engine
module imports React, browser APIs, network APIs, locale, timers or wall-clock time.
UI strings stay in `src/i18n`; engine config errors and event kinds are structured
codes for future localization. Language state lives entirely outside engine state.

Example engine usage:

```ts
import {
  presets, createSimulation, advanceSimulation, configureSimulation,
  getSimulationSnapshot, resetSimulation,
} from './src/engine';

let state = createSimulation(presets.trafficSpike);
state = advanceSimulation(state, 1000);
const snapshot = getSimulationSnapshot(state);
// snapshot.window names the latest completed simulated second explicitly.
state = configureSimulation(state, { ...state.config, cacheEnabled: true });
state = advanceSimulation(state, 1000);
state = resetSimulation(state.config);
```

`advanceSimulation` takes state plus delta (config is stored in state to prevent
accidental edits). `configureSimulation` explicitly applies edits at `nowMs`.
`resetSimulation` recreates the full seed/config baseline. Pause means no advance;
zero delta also returns the unchanged state. P1.3 owns start/pause/reset UI and clock.

## Safe implementation assumptions

These clarify implementation details without reopening approved decisions:

- Arrivals are evenly spaced, first at `1000 / incomingRps` ms, not an initial burst.
  Seeded LCG draws select cache HITs only when cache is enabled and the limiter admits.
  No unapproved arrival jitter/distribution was introduced. Same config, seed and
  edit sequence repeat exactly; positive time chunk sizes do not change outcomes.
- Scheduled timestamps are rounded to nanosecond precision in millisecond units.
  Arrival times derive from a phase anchor and index rather than accumulated periods.
- On a tie, close a metric bucket first, then complete all successes in request-ID
  order, then fill slots from FIFO, then process arrivals. Thus bucket intervals
  are half-open `[startMs, endMs)`. An arrival exactly at 1000ms belongs to bucket
  `[1000, 2000)`, not `[0, 1000)`. Initial `[0,1000)` therefore has one fewer arrival
  than the configured RPS; subsequent settled one-second windows match demand.
- Snapshots expose the **latest completed 1s window**, including its start/end, and
  instantaneous gauges at `nowMs`. Before a complete second, `window` is null;
  a complete window with no successes has `p95Ms: null`. UI must show an empty state,
  never substitute theoretical latency. Queue wait samples are measured at origin
  start; successful p95 samples are end-to-end durations measured at completion.
- Cache HIT statistics use an admission cohort: actual HIT decisions divided by
  limiter-admitted eligible GETs with admission timestamps in that bucket. This is
  `observedCacheHitRate`, distinct from configured probability and from completed
  cache responses. Its numerator can include a response still pending for 10ms;
  the future UI must label this as observed admission HIT fraction. Successful
  throughput and `completedCacheHits` count **only actual scheduled completions**.
  This cohort choice avoids dividing completions from prior demand by a new, lower
  admission count, which could misleadingly exceed 100%.
- Limiter starts full on reset or re-enable. Refill under the old rate is settled
  before an edit; changing the cap clamps tokens, never grants another full burst.
  Rejected 429s never reach the cache. All other arrivals increment eligible admitted
  count, including origin requests that later receive queue-overflow 503.
- Changing incoming RPS starts a new phase at the edit timestamp, with the first
  arrival one new interval later; counters/history are retained. Changing seed
  requires reset. Service time is captured at origin start; cache completion delay
  is captured at HIT admission. Neither is rewritten by later edits.
- Decreasing queue/slot capacity preserves accepted work. Gauges can temporarily
  exceed the new target, with new admissions/starts blocked appropriately. Manual
  instance edits set active capacity. `setActiveInstanceCount` exposes the scheduler
  seam for a future policy; P1.4 must enforce its stricter safe scale-in guard.
- Each explicit advance is finite and 0–60,000ms; invalid deltas throw. This is an
  engine work bound, not a wall-clock catch-up policy. P1.3 must cap/pause browser
  resume gaps rather than calling repeated advances to catch up real elapsed time.
- History retains 120 one-second buckets, each with raw completion/wait samples,
  and 240 transient events. There are no all-time request or latency arrays.
  Pending work is bounded by 1000 waiting, 160 origin requests and approximately
  five cache responses at canonical maximum demand. Cumulative scalar counters
  remain all-time; the event log is explicitly a recent, non-exhaustive trace.
- Engine validation permits cache probability 100% for invariant tests. P1.3 UI
  must enforce the approved 0–80% range. All other canonical limits are validated.
- English is the initial locale; no preference storage, external fonts or tracking.
  A conceptual static diagram is explicitly labeled as an illustration, not activity.
